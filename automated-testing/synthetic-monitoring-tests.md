# Synthetic Monitoring Tests

Synthetic Monitoring Tests are a set of functional tests that target a live system in production. The focus of these tests, which are sometimes named "watchdog", "active monitoring" or "synthetic transactions", is to verify the product's health and resilience continuously.

## Why Synthetic Monitoring Tests

Traditionally, software providers rely on testing through CI/CD stages in the well known testing pyramid (unit, integration, e2e) to validate that the product is healthy and without regressions. Such tests will run on the build agent or in the test/stage environment before being deployed to production and released to live user traffic. During the services' lifetime in the production environment, they are safeguarded by monitoring and alerting tools that rely on Real User Metrics/Monitoring (RUM).

However, as more organizations today provide highly-available (99.9+ SLA) products, they find that the nature of long-lived distributed applications, which typically rely on several hardware and software components, is to fail. Frequent releases (sometimes multiple times per day) of various components of the system can create further instability. This rapid rate of change to the production environment tends to make testing during CI/CD stages not hermetic and actually not representative of the end user experience and how the production system actually behaves.

For such systems, the ambition of service engineering teams is to reduce to a minimum the time it takes to fix errors, or the MTTR - Mean Time To Repair. It is a continuous effort, performed on the live/production system. Synthetic Monitors can be used to detect the following issues:

- Availability - Is the system or specific region available.
- Transactions and customer journeys - Known good requests should work, while known bad requests should error.
- Performance - How fast are actions and is that performance maintained through high loads and through version releases.
- 3rd Party components - Cloud or software components used by the system may fail.

### Shift-Right Testing

Synthetic Monitoring tests are a subset of tests that run in production, sometimes named Test-in-Production or Shift-Right tests. With Shift-Left paradigms that are so popular, the approach is to perform testing as early as possible in the application development lifecycle (i.e., moved left on the project timeline). Shift right compliments and adds on top of Shift-Left. It refers to running tests late in the cycle, during deployment, release, and post-release when the product is serving production traffic. They provide modern engineering teams a broader set of tools to assure high SLAs over time.

## Synthetic Monitoring Tests Design Blocks

A synthetic monitoring test is a test that uses synthetic data and real testing accounts to inject user behaviors to the system and validates their effect, usually by passively relying on existing monitoring and alerting capabilities. Components of synthetic monitoring tests include Probes, test code/ accounts which generates data, and Monitoring tools placed to validate both the system's behavior under test and the health of the probes themselves.

### Probes

Probes are the source of synthetic user actions that drive testing. They target the product's front-end or publicly-facing APIs and are running on their own production environment. A Synthetic Monitoring test is, in fact, very related to black-box tests and would usually focus on end-to-end scenarios from a user's perspective. It is not uncommon for the same code for e2e or integration tests to be used to implement the probe.

### Monitoring

Given that Synthetic Monitoring tests are continuously running, at intervals, in a production environment, the assertion of system behavior through analysis relies on existing monitoring pillars used in live system (Logging, Metrics, Distributed Tracing). There would usually be a finite set of tests, and key metrics that are used to build monitors and alerts to assert against the known SLO, and verify that the OKR for that system are maintained. The monitoring tools are effectively capturing both RUMs and synthetic data generated by the probes.

## Applying Synthetic Monitoring Tests

### Asserting the System under Test

Synthetic monitoring tests are usually statistical. Test metrics are compared against some historical or running average with a time dimension (Example: Over the last 30 days, for this time of day, the mean average response time is 250ms for AddToCart operation with a standard deviation from the mean of +/- 32ms). So if an observed measurement is within a deviation of the norm at any time, the services are probably healthy.

### Building a Synthetic Monitoring Solution

At a high level, building synthetic monitors usually consists of the following steps:

- Determine the metric to be validated (functional result, latency, etc.)
- Build a piece of automation that measures that metric against the system, and gathers telemetry into the system's existing monitoring infrastructure.
- Set up monitoring alarms/actions/responses that detect the failure of the system to meet the desired goal of the metric.
- Run the test case automation continuously at an appropriate interval.

### Monitoring the Health of Tests

Probes runtime is a production environment on its own, and the health of tests is critical. Many providers offer cloud-based systems that host such runtimes, while some organizations use existing production environments to run these tests on. In either way, a monitor-the-monitor strategy should be a first-class citizen of the production environment's alerting systems.

### Synthetic Monitoring and Real User Monitoring

Synthetic monitoring does not replace the need for RUM. Probes are predictable code that verifies specific scenarios, and they do not 100% completely and truly represent how a user session is handled. On the other hand, prefer not to use RUMs to test for site reliability because:

- As the name implies, RUM requires user traffic. The site may be down, but since no user visited the monitored path, no alerts were triggered yet.
- Inconsistent Traffic and usage patterns make it hard to gauge for benchmarks.

### Risks

Testing in production, in general, has a risk factor attached to it, which does not exist tests executed during CI/CD stages. Specifically, in synthetic monitoring tests, the following may affect the production environment:

- Corrupted or invalid data - Tests inject test data which may be in some ways corrupt. Consider using a testing schema.
- Protected data leakage - Tests run in a production environment and emit logs or trace that may contain protected data.
- Overloaded systems - Synthetic tests may cause errors or overload the system.
- Unintended side effects or impacts on other production systems.
- Skewed analytics (traffic funnels, A/B test results, etc.)
- Auth/AuthZ - Tests are required to run in production where access to tokens and secrets may be restricted or more challenging to retrieve.

## Synthetic Monitoring Tests Frameworks and Tools

Most key monitoring/APM players have an enterprise product that supports synthetic monitoring built into their systems (see list below). Such offerings make some of the risks raised above irrelevant as the integration and runtime aspects of the solution are OOTB. However, such solutions are typically pricey.

Some organizations prefer running probes on existing infrastructure using known tools such as Postman, Wrk, JMeter, Selenium or even custom code to generate the synthetic data. Such solutions must account for isolating and decoupling the probe's production environment from the core product's as well as provide monitoring, geo-distribution, and maintaining test health.

- Application Insights availability - Simple availability tests that allow some customization using Multi-step web test
- DataDog Synthetics
- Dynatrace Synthetic Monitoring
- New Relic Synthetics
- Checkly

## Conclusion

The value of production tests, in general, and specifically Synthetic monitoring, is only there for particular engagement types, and there is associated risk and cost to them. However, when applicable, they provide continuous assurance that there are no system failures from a user's perspective. When developing a PaaS/SaaS solution, Synthetic monitoring is key to the success of service reliability teams, and they are becoming an integral part of the quality assurance stack of highly available products.

# 合成监控测试

合成监控测试（Synthetic Monitoring Tests）是一组针对生产环境中实时系统的功能测试。这类测试有时被称为“看门狗（watchdog）”“主动监控（active monitoring）”或“合成事务（synthetic transactions）”，其核心目标是持续验证产品的健康度与韧性。

## 为什么需要合成监控测试

传统上，软件提供商依赖在 CI/CD 各阶段中、按照众所周知的测试金字塔（单元测试、集成测试、端到端测试）进行测试，以验证产品健康且无回归。这类测试会在构建代理上、或在测试/预发布环境中运行，之后才部署到生产环境并面向真实用户流量发布。在服务于生产环境运行的整个生命周期中，它们由依赖真实用户指标/监控（Real User Metrics/Monitoring，RUM）的监控与告警工具来守护。

然而，随着如今越来越多的组织提供高可用（99.9+ SLA）产品，他们发现：长期运行的分布式应用本质上就是会出故障的，这类应用通常依赖多个硬件与软件组件。系统各组件的高频发布（有时一天多次）会进一步加剧不稳定性。生产环境这种快速的变化节奏，往往使得 CI/CD 阶段的测试不再“封闭（hermetic）”，实际上也无法代表最终用户体验以及生产系统的真实行为。

对于这类系统，服务工程团队的目标是把修复错误所需的时间——即 MTTR（Mean Time To Repair，平均修复时间）——降到最低。这是一项在实时/生产系统上持续进行的工作。合成监控可用于检测以下问题：

- 可用性——系统或特定区域是否可用。
- 事务与客户旅程——已知的“好”请求应当成功，已知的“坏”请求应当报错。
- 性能——操作有多快，以及在高负载和版本发布过程中该性能是否得以保持。
- 第三方组件——系统所使用的云或软件组件可能发生故障。

### 右移测试（Shift-Right Testing）

合成监控测试是在生产环境中运行的测试的一个子集，有时被称为“生产环境测试（Test-in-Production）”或“右移测试（Shift-Right tests）”。在“左移（Shift-Left）”范式如此流行的背景下，其思路是尽可能早地在应用开发生命周期中进行测试（即在项目时间线上向左移动）。右移是对左移的补充与叠加，指的是在周期后期——即部署、发布及发布后、产品正在服务生产流量时——运行测试。它们为现代工程团队提供了更广泛的工具集，以长期保障高 SLA。

## 合成监控测试的设计要素

合成监控测试是一种使用合成数据和真实测试账号向系统注入用户行为、并验证其效果的测试，通常通过被动地依赖现有的监控与告警能力来实现。合成监控测试的组成部分包括：探针（Probes）、生成数据的测试代码/账号，以及用于同时验证被测系统行为与探针自身健康度的监控工具。

### 探针（Probes）

探针是驱动测试的合成用户行为的来源。它们以产品的前端或公开 API 为目标，并运行在它们自己的生产环境中。合成监控测试实际上与黑盒测试非常接近，通常聚焦于从用户视角出发的端到端场景。用同一份端到端或集成测试代码来实现探针的情况并不少见。

### 监控（Monitoring）

由于合成监控测试是在生产环境中按一定间隔持续运行的，因此通过分析来断言系统行为，需要依赖实时系统中已有的监控支柱（日志 Logging、指标 Metrics、分布式追踪 Distributed Tracing）。通常会有一组有限的测试和关键指标，用于构建监控与告警，以对照已知的 SLO 进行断言，并验证该系统的 OKR 是否得到维持。监控工具实际上同时采集 RUM 数据与探针生成的合成数据。

## 应用合成监控测试

### 断言被测系统

合成监控测试通常是统计性的。测试指标会与某个带有时间维度的历史或滚动平均值进行比较（例如：在过去 30 天中、每天的同一时段，AddToCart 操作的平均响应时间为 250ms，均值的标准差为 +/- 32ms）。因此，如果某一时刻观测到的测量值处于正常值的偏差范围之内，那么服务大概率是健康的。

### 构建合成监控方案

从高层来看，构建合成监控通常包含以下步骤：

- 确定要验证的指标（功能结果、延迟等）。
- 构建一段自动化，针对系统测量该指标，并将遥测数据汇聚到系统现有的监控基础设施中。
- 设置监控告警/动作/响应，以检测系统未能达到该指标期望目标的情况。
- 以适当的间隔持续运行该测试用例自动化。

### 监控测试自身的健康度

探针运行时本身就是一个生产环境，测试的健康度至关重要。许多厂商提供托管此类运行时的云系统，而一些组织则使用现有的生产环境来运行这些测试。无论哪种方式，“监控监控者（monitor-the-monitor）”策略都应当是生产环境告警系统中的一等公民。

### 合成监控与真实用户监控

合成监控并不能取代对 RUM 的需求。探针是验证特定场景的可预测代码，它们并不能 100% 完整、真实地代表用户会话是如何被处理的。另一方面，也不建议用 RUM 来测试站点可靠性，原因如下：

- 顾名思义，RUM 需要用户流量。站点可能已经宕机，但由于没有用户访问被监控的路径，告警尚未触发。
- 不一致的流量与使用模式使得难以进行基准衡量。

### 风险

一般而言，生产环境测试带有一定的风险因素，这是 CI/CD 阶段执行的测试所不具备的。具体到合成监控测试，以下因素可能影响生产环境：

- 数据损坏或无效——测试注入的测试数据可能在某种程度上是损坏的。可考虑使用测试专用的 schema。
- 受保护数据泄露——测试在生产环境中运行，并可能输出包含受保护数据的日志或追踪。
- 系统过载——合成测试可能导致错误或使系统过载。
- 对其他生产系统产生非预期的副作用或影响。
- 分析数据失真（流量漏斗、A/B 测试结果等）。
- 认证/授权（Auth/AuthZ）——测试需要在生产环境中运行，而生产环境中对令牌和密钥的访问可能受限或更难获取。

## 合成监控测试的框架与工具

大多数主流监控/APM 厂商都在其系统中内置了支持合成监控的企业级产品（见下方列表）。这类产品使上述部分风险变得无关紧要，因为方案的集成与运行时方面都是开箱即用（OOTB）的。然而，这类方案通常价格不菲。

一些组织更倾向于在现有基础设施上使用诸如 Postman、Wrk、JMeter、Selenium 等已知工具，甚至自定义代码来生成合成数据、运行探针。这类方案必须自行处理探针生产环境与核心产品生产环境的隔离与解耦，并提供监控、地理分布以及测试健康度的维护。

- Application Insights 可用性测试——简单的可用性测试，可通过多步骤 Web 测试（Multi-step web test）进行一定程度的定制
- DataDog Synthetics
- Dynatrace Synthetic Monitoring
- New Relic Synthetics
- Checkly

## 结论

一般而言，生产环境测试、尤其是合成监控的价值，只存在于特定类型的项目（engagement）中，并且伴随着相应的风险与成本。然而，在适用的情况下，它们能够持续提供“从用户视角看系统没有故障”的保证。在开发 PaaS/SaaS 解决方案时，合成监控是服务可靠性团队成功的关键，并且正日益成为高可用产品质量保障栈中不可或缺的一部分。

## 摘要

本文是 Microsoft“Code With Engineering Playbook”（代码工程手册）中“自动化测试”章节下的一篇工程实践指南，系统阐述了“合成监控测试（Synthetic Monitoring Tests）”这一概念。文章将合成监控测试定义为“针对生产环境中实时系统的一组功能测试”，属于“右移测试（Shift-Right Testing）/生产环境测试（Test-in-Production）”的范畴，用于持续验证高可用产品的健康度与韧性。文章的核心逻辑是：传统 CI/CD 阶段的测试无法真实反映生产系统的行为，而高可用分布式系统“本质上就会出故障”，因此需要主动、持续地在生产环境注入合成用户行为，以检测可用性、客户旅程、性能与第三方组件故障，从而降低 MTTR。文章进一步给出了合成监控的设计要素（探针与监控）、统计性断言方法、构建步骤、与 RUM 的互补关系、生产环境测试的风险，以及主流工具选型（企业级托管产品 vs 自托管开源工具），并强调“监控监控者”策略应是一等公民。

| Black-box Testing | 黑盒测试 | 在不查看内部结构/源码的情况下，仅根据输入与预期输出来验证功能，关注用户视角。合成监控测试与黑盒测试非常接近，通常聚焦端到端场景 [🔗](https://en.wikipedia.org/wiki/Black-box_testing "Wikipedia — Black-box testing") |
| Standard Deviation | 标准差（σ） | 衡量数据围绕均值离散程度的统计量，在统计监控中用于定义异常检测阈值。文章中的“250ms ± 32ms”即用均值与标准差刻画历史基线，观测值落在偏差范围内则判定服务健康 [🔗](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc231.htm "NIST — Control chart for standard deviations") |
| Monitor-the-monitor | 元监控 / “监控监控者”策略 | 监控监控系统本身，并在监控系统失效时告警。核心难题是“监控系统无法可靠地监控自身的故障”，因此需要独立的、处于不同故障域的观察者（如“死人手开关”心跳） [🔗](https://grafana.com/docs/grafana/latest/alerting/set-up/meta-monitoring/ "Grafana — Meta monitoring") |
| Auth/AuthZ | Authentication / Authorization（认证 / 授权） | 认证（AuthN）验证“你是谁”，授权（AuthZ）决定“你能做什么”。在生产环境运行合成测试时，获取令牌和密钥可能受限，这是测试面临的实际挑战之一 [🔗](https://learn.microsoft.com/en-us/entra/identity-platform/authentication-vs-authorization "Microsoft Learn — Authentication vs. authorization") |
| APM | Application Performance Monitoring（应用性能监控） | 使用软件工具与遥测数据实时监控、测量和管理业务关键应用的性能与可用性，目标是在影响最终用户之前检测、诊断并解决性能问题。主流 APM 厂商通常内置合成监控能力 [🔗](https://aws.amazon.com/what-is/application-performance-monitoring/ "AWS — What is APM?") |

## 深度解读

### 核心论点：为什么“测试金字塔”不够了

文章的核心论点建立在一个清晰的逻辑链条上：传统测试金字塔（单元、集成、端到端）在 CI/CD 阶段运行，其前提是测试环境能够“封闭地（hermetic）”复现生产行为。但文章指出，对于高可用（99.9+ SLA）的分布式系统，这一前提正在失效——长期运行的系统“本质上就会出故障”，而一天多次的高频发布进一步加剧了不稳定性，使得 CI/CD 阶段的测试“不再封闭，实际上也无法代表最终用户体验”。

这一论点的价值在于，它把合成监控从“锦上添花的监控手段”重新定位为“质量保障的必要补充”。文章用 MTTR 作为连接点：既然故障不可避免，那么工程团队的目标就从“防止故障”转向“最小化修复时间”，而合成监控正是通过主动、持续地探测生产系统来缩短“故障发生”到“故障被发现”之间的时间差。这与 Google SRE 的理念一脉相承——SRE 手册将测试分为“传统测试”与“生产测试”，并强调生产测试对运行可靠服务必不可少 [🔗](https://sre.google/sre-book/testing-reliability/ "Google SRE Book — Testing for Reliability")。

### 背景与语境：右移测试的兴起

文章将合成监控明确归入“右移测试（Shift-Right Testing）”的范畴，这是理解本文时代背景的关键。在 DevOps 运动早期，“左移（Shift-Left）”是主流口号——把测试尽可能提前到开发早期，以降低缺陷修复成本。但左移无法解决一个根本问题：有些故障只有在真实生产流量、真实数据、真实第三方依赖下才会暴露。

Microsoft 官方文档将“右移”定义为“把部分测试推迟到 DevOps 流程后期，在生产环境中进行测试”，并明确它与左移“互补” [🔗](https://learn.microsoft.com/en-us/devops/deliver/shift-right-test-production "Microsoft Learn — Shift right to test in production")。文章正是站在这一立场上：右移不是对左移的否定，而是“补充与叠加”。这一立场值得注意——它避免了“左移 vs 右移”的二元对立，而是主张两者共同构成完整的质量保障体系。

### 技术维度：探针、统计断言与“监控监控者”

文章的技术贡献在于给出了合成监控的三个设计要素，其中两个尤其值得深入：

**其一，探针（Probes）与黑盒测试的等价性。** 文章指出合成监控测试“实际上与黑盒测试非常接近”，且“用同一份端到端或集成测试代码来实现探针的情况并不少见”。这是一个重要的工程洞察：合成监控并非一套全新的测试技术，而是对既有测试资产的“生产化复用”。这意味着团队可以以较低成本将已有的端到端测试改造为持续运行的探针。

**其二，统计性断言而非布尔断言。** 文章强调合成监控测试“通常是统计性的”——将观测值与带时间维度的历史滚动平均值比较（如“过去 30 天同时段 AddToCart 平均响应 250ms，标准差 ±32ms”），落在偏差范围内即判定健康。这与传统测试的“通过/失败”二元判定有本质区别：它承认生产系统的性能天然存在波动，用统计基线而非固定阈值来区分“正常波动”与“真实异常”。这一方法在 APM 领域是标准实践（基于基线的异常检测），但文章将其清晰地提炼为合成监控的判定范式。

**其三，“监控监控者”策略。** 文章特别强调探针运行时“本身就是一个生产环境”，因此“监控监控者策略应当是一等公民”。这是一个容易被忽视但至关重要的点：如果探针自身宕机而无人知晓，合成监控就会产生“虚假的安全感”。业界对此的标准解法是“死人手开关（Dead Man's Switch）”——一个始终触发的心跳告警，一旦监控管道失效，心跳停止，独立的外部服务通过独立通道告警 [🔗](https://grafana.com/docs/grafana/latest/alerting/set-up/meta-monitoring/ "Grafana — Meta monitoring")。

### 影响与意义：合成监控与 RUM 的边界

文章对“合成监控 vs RUM”的辨析是其最有实践价值的部分之一。它给出了一个清晰、可操作的判断标准：

- **合成监控**是“可预测的代码”，验证特定场景，是主动的、确定性的；
- **RUM** 需要真实用户流量，是被动的、依赖流量的。

文章由此得出两个反直觉但正确的结论：其一，合成监控不能取代 RUM（因为探针无法 100% 真实代表用户会话）；其二，也不该用 RUM 来测站点可靠性（因为“站点可能已经宕机，但由于没有用户访问被监控路径，告警尚未触发”）。这一“双向不可替代”的论述，纠正了实践中常见的“有了 RUM 就不需要合成监控”或“有了合成监控就不需要 RUM”的误区，与 Datadog 等厂商的官方立场一致 [🔗](https://www.datadoghq.com/blog/rum-synthetic-monitoring-together/ "Datadog — Optimize your frontend monitoring strategy with Synthetic Monitoring and RUM")。

### 争议与风险：生产环境测试的代价

文章并未回避合成监控的争议面，而是用一整节列举了六类风险：数据损坏、受保护数据泄露、系统过载、对其他系统的副作用、分析数据失真、以及认证/授权难题。这体现了文章的严谨性——它明确承认“生产环境测试带有风险因素，这是 CI/CD 阶段测试所不具备的”。

值得注意的是文章在“结论”中的克制表述：合成监控的价值“只存在于特定类型的项目中，并伴随风险与成本”。这与一些厂商营销材料中“合成监控是万能解药”的论调形成对比。文章实际上划定了合成监控的适用边界：它最适合“开发 PaaS/SaaS 解决方案”且追求高 SLA 的场景，而非所有项目。这种“有条件适用”的判断，反而增强了文章作为工程实践指南的可信度。

### 工具选型：托管 vs 自托管的权衡

文章将工具分为两类，并给出了清晰的权衡逻辑：

- **企业级托管产品**（Application Insights、Datadog Synthetics、Dynatrace、New Relic Synthetics、Checkly）：集成与运行时开箱即用，使部分风险“无关紧要”，但“通常价格不菲”；
- **自托管开源工具**（Postman、Wrk、JMeter、Selenium 或自定义代码）：成本低、可控性强，但必须自行处理环境隔离、监控、地理分布与测试健康度维护。

这一分类的洞察在于：托管产品的溢价，本质上买的是“把风险外包”——厂商替你解决了探针运行时的隔离、地理分布和健康度监控这些“监控监控者”难题。而自托管方案省下的钱，需要以工程团队自行承担这些运维负担为代价。文章没有偏袒任何一方，而是把决策权留给读者根据自身情况权衡。

### 总结

本文是一篇高质量、克制而严谨的工程实践指南。它没有停留在“合成监控是什么”的科普层面，而是深入回答了“为什么需要它”（高可用分布式系统本质会故障、CI/CD 测试不再封闭）、“它如何工作”（探针 + 统计性断言 + 监控监控者）、“它与 RUM 的边界”（双向不可替代）、“它的代价”（六类生产环境风险）以及“如何选型”（托管 vs 自托管的权衡）。文章的可信度较高：它出自 Microsoft 官方开源工程手册，引用了 Google SRE 手册、Microsoft 官方文档和 Martin Fowler 博客等权威资料，且对合成监控的适用边界保持了难得的克制。其唯一的小瑕疵是两处引用细节不精确（Google SRE 章节标题、Martin Fowler 文章的实际作者），但不影响核心论点的正确性。

**关键要点：**

- 合成监控测试是“右移测试”的一种，通过主动、持续地在生产环境注入合成用户行为，弥补传统 CI/CD 测试无法反映生产真实行为的缺陷，核心目标是降低 MTTR。
- 其技术本质是“黑盒测试的生产化复用”——探针常由既有的端到端/集成测试代码改造而来，判定方式从二元“通过/失败”升级为基于历史基线的统计性断言。
- 合成监控与 RUM 是“双向不可替代”的互补关系：合成监控主动但无法完全代表真实用户，RUM 真实但依赖流量、可能漏报宕机。
- 生产环境测试有六类固有风险（数据损坏、数据泄露、过载、副作用、分析失真、认证授权），托管产品通过“开箱即用”外包了部分风险，但价格更高。
- “监控监控者”策略是合成监控的一等公民——探针运行时本身也是生产环境，其自身健康度必须被独立监控。
