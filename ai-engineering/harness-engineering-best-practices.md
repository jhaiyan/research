## 1. 分层上下文设计

### 原则：上下文是稀缺资源，不是越多越好

实验数据显示，上下文窗口使用率超过约 40% 时，Agent 质量开始下滑。给 Agent 塞大量工具定义、冗长文档和对话历史，不会让它更聪明——反而会让它变笨。

### 三层加载模型

| 层级 | 加载时机 | 内容示例 | 上下文占用 |
| --- | --- | --- | --- |
| **Tier 1：会话常驻** | 每次会话自动加载 | AGENTS.md / CLAUDE.md、项目结构概览 | 最小（目标 < 60 行） |
| **Tier 2：任务相关** | 进入特定目录时加载 | 子系统专属规则、局部 AGENTS.md | 中等 |
| **Tier 3：按需检索** | 工具调用或 Agent 主动请求 | 设计文档、API 参考、执行计划 | 受控 |

### 实操建议

- **AGENTS.md 保持精简**：目标控制在 60 行以内。每增加一行，都要问自己“这行不在会不会让 Agent 出错？”
- **小型入口文件 + 深层链接**：根目录 AGENTS.md 只列出关键原则和“如何找到更多信息”的指针，而非一个巨大的指令文件
- **子目录 AGENTS.md**：在各子系统目录放置局部规则，Agent 只在进入该目录时才加载
- **代码仓库是唯一事实源**：Slack 消息、Google Docs、人脑中的知识对 Agent 等于不存在。所有规范必须以版本控制的文件（代码、Markdown、Schema、执行计划）存放在仓库中

## 2. 引导系统（前馈控制）

### 原则：帮 Agent 第一次就做对，而不是事后修补

引导（Guides）是在 Agent 行动*之前*预测并引导其行为的机制，目标是提高首次产出良好结果的概率。

### AGENTS.md / CLAUDE.md 的写法

**每一行规则背后，对应一次历史失败。** Mitchell Hashimoto 的 Ghostty 项目中，AGENTS.md 的每条规则都来自 Agent 真实犯过的错。这是最重要的写作原则。

**推荐结构**：

```markdown
# [项目名] Agent 指南

## 快速上手
- 如何启动开发服务器：`<命令>`
- 如何运行测试：`<命令>`
- 代码风格检查：`<命令>`

## 架构原则（必须遵守）
- [规则 1，附修复方向]
- [规则 2，附修复方向]

## 常见陷阱（历史失败案例）
- 不要做 X，因为 Y，应该改用 Z
- 不要修改 A 目录，应该通过 B 接口操作

## 更多信息
- 架构设计：docs/architecture.md
- API 规范：docs/api-spec.md
- 执行计划模板：docs/plan-template.md
```

**明确告知如何启动项目**：Agent 每次新会话最浪费的 token，是在弄清楚“怎么运行这个应用”上。在 AGENTS.md 中明确写出开发服务器启动命令、测试命令、构建命令。

### 架构引导文档

在代码仓库中维护机器可读的架构决策记录（ADR）：

- 明确的依赖方向约束（如 `Types → Config → Repo → Service → Runtime → UI`）
- 每个业务域的职责边界
- 禁止的模式及替代方案

### “正向提示注入”模式

设计工具和脚本的输出时，**在错误消息中直接告诉 Agent 如何修复**，而不仅仅是报告错误：

```text
# 差的错误消息：
ERROR: Circular dependency detected in module 'auth'

# 好的错误消息：
ERROR: Circular dependency detected: auth → user → auth
FIX: Move the shared type definition to types/auth.ts, 
     then import from there in both auth/ and user/.
See docs/architecture.md#dependency-rules for the full dependency graph.
```

这让工具在 Agent 工作时同时“教会”它——每次执行即一次引导。

## 3. 传感器系统（反馈控制）

### 原则：质量左移，越早发现问题修复成本越低

传感器（Sensors）是在 Agent 行动*之后*观察结果、帮助其自我修正的机制。

### 按交付生命周期分布传感器

| 时机 | 速度要求 | 适用传感器 |
| --- | --- | --- |
| **提交前（Pre-commit）** | 秒级 | Linter、快速单元测试、基础代码审查 Agent |
| **集成后（CI Pipeline）** | 允许较慢 | 变异测试、全面代码审查、架构约束检查 |
| **持续漂移监控** | 后台运行 | 死代码检测、测试覆盖质量分析、依赖扫描 |
| **运行时反馈** | 持续采样 | SLO 退化监控、日志异常标记、响应质量采样 |

### 计算型传感器 vs. 推理型传感器

| 类型 | 特点 | 适用场景 |
| --- | --- | --- |
| **计算型** | 确定性、毫秒到秒级、低成本 | 结构检查、测试、Lint、类型检查 |
| **推理型（LLM）** | 非确定性、较慢、较贵，但能做语义判断 | 代码审查 Agent、“LLM as Judge”评估 |

**优先构建计算型传感器**：它们足够快，可以在每次变更时运行，并且结果可靠。推理型传感器用于弥补计算型传感器的语义盲区。

### 传感器输出优化

传感器的输出必须为 LLM 消费而优化：

- **单行错误格式**：`ERROR: [module] [reason]`（易于 grep，不浪费 token）
- **错误消息包含修复指令**（见上节“正向提示注入”）
- **成功时保持静默**：只在出错时输出，避免污染上下文
- **预计算聚合统计**：`Coverage: 78% (target: 80%)` 而非输出原始数据

### 行为验证（当前最难的部分）

功能正确性验证是 Harness 三大类别中最难的，现有手段：

- **端到端浏览器自动化**：通过 Puppeteer/Playwright MCP 让 Agent 真正点击页面、查 API、看数据库状态——而不是只看代码或截图打分
- **生成 + 评估分离架构**：Generator 写代码，独立 Evaluator 像真人 QA 一样操作后给反馈
- **变异测试**：验证测试套件本身的质量，而不只是测试是否通过
- **Approved Fixtures（预批准固件）**：在适用场景下使用人工预审的测试基准

**警告**：不要相信 Agent 对自己输出的自我评估。Anthropic 研究发现，让 Agent 评估自己刚写完的东西，它会自信地表示写得很好——即使人类看来质量明显不行。METR 研究数据：自动评分器对 Agent 能力的评估比人类维护者实际接受度高出 **7 倍**。

## 4. 架构约束的机械化执行

### 原则：文档记录不够，约束必须自动化

如果架构规则不能机械化地强制执行，Agent 就会偏离——不是因为它故意违反，而是因为它无法感受到“这样做不对”的审美反感。

### 实施步骤

#### Step 1：明确定义依赖方向

在代码仓库中明确记录分层架构和依赖方向，例如：

```text
Types → Config → Repository → Service → Runtime → UI
```

#### Step 2：用自定义 Linter 强制执行

为每条架构规则编写自动检测工具。关键点：让 Agent 生成 Linter 自身（用 Agent 写 Linter，然后 Linter 约束 Agent）。

```bash
# 示例：检测跨层依赖的自定义 Lint 规则
# 错误消息应直接包含修复指令
```

#### Step 3：用结构测试检验架构完整性

使用 ArchUnit（Java）、Dependency Cruiser（JavaScript）等工具，或自定义脚本，让架构规则成为可运行的测试。

#### Step 4：在 CI 中强制执行

架构约束检查必须进入 CI pipeline，失败时阻断合并。

### 为什么架构约束对 Agent 比对人类更重要

对人类团队，强架构约束有时感觉过于严苛；对 Agent 而言，**它们是乘数效应：一旦编码，便处处适用**。

> OpenAI 团队的经验：“这种架构通常要等到你拥有数百名工程师时才会引入。对于编码 Agent 来说，这是一个早期的先决条件：有了约束，速度才不会下降，架构才不会漂移。”

## 5. 熵管理与代码质量维护

### 原则：AI 生成的代码会自然积累熵，清理必须与生成同步

AI 生成的代码天然倾向于：

- 复现代码库中的已有模式（包括不好的模式）
- 重新实现已有功能（代码去重问题）
- 引入风格漂移

### 建立循环清理流程

**初期（人工阶段）**：每周安排固定时间（如 20% 的周五）人工清理 AI Slop，建立对典型问题的认知。

**中期（半自动阶段）**：

- 将清理标准编写成 Linter 规则和脚本
- 定期触发清理扫描，生成待处理列表

**成熟期（自动化阶段）**：

- 建立后台清理 Agent，定期扫描偏差、更新质量等级，发起有针对性的重构 PR
- 大多数清理 PR 可以一分钟内完成审查并自动合并
- **清理吞吐量应与代码生成吞吐量成正比扩展**

### 黄金原则的编码

将带主观意见的“黄金原则”（不仅仅是规范，还包括团队品味）编码到仓库中：

- 代码复杂度限制（函数行数、圈复杂度）
- 禁止的模式列表（带替代方案）
- 质量评级标准（各模块的当前健康度分数）

### 文档维护自动化

OpenAI 的实践：建立“doc-gardening” Agent，定期扫描过时或废弃的文档，发起修复 PR——**Agent 为 Agent 维护文档**。

## 6. 会话连续性管理

### 原则：进度保存在文件系统，而不是上下文窗口

每次新 Agent 会话从零开始，对之前发生的一切一无所知。这是当前所有 AI 编程工具的基本限制。

### 进度文件设计

**使用 JSON 而非 Markdown 追踪状态**：Agent 不太可能不恰当地修改或覆盖结构化数据。

```json
{
  "project": "my-app",
  "last_updated": "2026-04-07T10:30:00Z",
  "features": [
    {
      "id": "feat-001",
      "name": "用户登录",
      "status": "completed",
      "test_steps": ["访问 /login", "输入凭据", "验证 JWT 返回"],
      "notes": "已验证端到端，包括错误处理"
    },
    {
      "id": "feat-002", 
      "name": "密码重置",
      "status": "in_progress",
      "blocked_by": null,
      "notes": "邮件发送逻辑完成，UI 待实现"
    }
  ],
  "known_issues": [],
  "next_session_start": "继续 feat-002，从实现重置密码 UI 开始"
}
```

### 双 Agent 启动模式

适用于长时间运行的复杂项目：

1. **初始化 Agent（一次性）**：建立结构化功能列表、init.sh 脚本、初始 git 提交，所有功能初始标记 `failing`
2. **编码 Agent（反复运行）**：每次从进度文件读取状态，选择单个功能开始工作，完成后更新状态

### 会话结束时的标准产出

每次 Agent 会话结束时，应产出：

- 更新的进度文件
- 清晰的 git 提交（功能边界内的原子提交）
- 更新的 AGENTS.md（如有新发现的失败模式）

## 7. 任务分解与多 Agent 架构

### 原则：思考与执行分离，永远不要让 Agent 在审查计划之前写代码

> “永远不要让 Agent 在你审查和批准书面计划之前写代码。” —— Boris Tane, Cloudflare

### 规划优先工作流

```text
1. 研究阶段（只读 Agent）
   → 输出：调研报告、现有代码分析、风险识别

2. 规划阶段（只读 + 写计划文件）
   → 输出：分步执行计划（每步可独立验证）
   → 人类审查和批准计划 ← 关键检查点

3. 执行阶段（完整工具权限）
   → 按批准计划实现，每步完成后运行传感器

4. 验证阶段（只读 + 运行测试）
   → 独立评估 Agent 验证功能正确性
```

### 专业化 Agent 分工

| Agent 角色 | 职责 | 工具权限 |
| --- | --- | --- |
| **研究 Agent** | 探索代码库、分析实现细节 | 只读 |
| **规划 Agent** | 分解任务、创建执行计划 | 只读 + 写计划文件 |
| **执行 Agent** | 按批准计划实现代码 | 完整工具权限 |
| **评估 Agent** | 验证输出质量 | 只读 + 运行测试 |

**专业化本身就是上下文管理策略**：每个专家因为携带更少的无关信息，更容易保持在 “Smart Zone” 内工作。

### 工具精简原则

Stripe 内部有约 500 个 MCP 工具，但给每个 Agent 精心筛选的子集。**更多的工具不等于更好的表现**。

工具选择原则：

- 如果功能已有训练良好的 CLI（如 `git`、`gh`、`docker`），优先用 CLI 而不是新增 MCP 工具
- 每增加一个工具，都要评估它带来的价值是否超过上下文膨胀的代价
- 为不同任务类型准备不同的工具子集

### 并发控制

**Stripe 的硬规则**：CI 最多跑两轮。第一轮失败，Agent 自动修复再跑一次；还失败，直接转交人类。**不允许 Agent 在 CI 上无限重试**。

## 8. 可观测性集成

### 原则：让 Agent 能直接查询和感知运行时状态

离开运行时反馈，Agent 只能通过代码猜测系统行为。连接可观测性数据，让 Agent 成为能实际验证自己工作的工程师。

### 可观测性接入方式

**前端/浏览器**：

- 通过 Chrome DevTools 协议接入 Agent 运行时
- 提供 DOM 快照、截图和导航能力（Puppeteer/Playwright MCP）
- 注意：Agent 看不到浏览器原生 alert 弹窗——需要用其他方式处理

**日志与指标**：

- 通过 LogQL 接口暴露日志查询能力
- 通过 PromQL 接口暴露指标查询能力
- Agent 能查询“这个请求花了多少时间？”而不是猜测

**可度量的性能目标**：

- 将具体性能目标（如“服务启动必须在 800ms 内完成”）连接到可查询的指标
- 让 Agent 能验证“我的改动是否满足了性能要求”

### 会话隔离

OpenAI 的实践：每次任务完成后，该任务的独立应用实例和所有日志/指标自动清除。这避免了跨会话的状态污染。

## 9. Harness 的持续演进

### 原则：每次 Agent 犯错，就工程化一个解决方案确保不再犯同样的错误

这是 Harness Engineering 的核心循环：

```text
Agent 犯错
   ↓
分析根本原因：
  - 缺少引导（前馈）？→ 更新 AGENTS.md，添加规则
  - 缺少传感器（反馈）？→ 添加 Linter 规则或测试
  - 工具不足？→ 构建新工具并在 AGENTS.md 中声明
  - 任务分解问题？→ 调整任务粒度或规划流程
   ↓
工程化解决方案（使此类错误在系统层面不可能再发生）
   ↓
下次 Agent 不会犯同样的错
```

### Harness 随模型升级的演化

随着模型能力提升，Harness 需要主动重新审视：

- **拆掉过时约束**：Anthropic 的经验表明，升级到 Opus 4.6 后，原来用于补偿“上下文焦虑”的 sprint 结构可以完全移除
- **打开新的高阶约束空间**：模型越强，能委托的任务越复杂，新的约束需求会随之出现
- **定期审计 AGENTS.md**：标记陈旧规则，移除不再适用的约束

**模型升级时的 Harness 审计清单**：

1. 哪些传感器是为了补偿旧模型的已知局限而存在的？
2. 哪些 AGENTS.md 规则是针对旧模型行为的？
3. 任务分解粒度是否还合适？
4. 上下文管理策略是否需要调整？

### 优先级排序

如果从零开始建设 Harness，按优先级：

1. **立即**：在 AGENTS.md 中记录每次 Agent 失败和对应的规则
2. **第一周**：为 1-2 个最关键的架构边界写自动化 Linter（错误消息包含修复指令）
3. **第一个月**：建立会话连续性机制（进度 JSON 文件），把散落各处的规范迁入仓库
4. **成熟期**：建立循环清理流程，逐步扩展到自动化后台清理 Agent

## 10. 反模式警示

### 反模式 1：巨大的单一 AGENTS.md

一个塞满了几百行规则的 AGENTS.md 会导致：

- 上下文浪费
- 信号稀释（一切都重要等于没有重要）
- 迅速腐烂成陈旧规则的坟场

**替代方案**：分层上下文设计（见第 1 节）

### 反模式 2：让 Agent 自我评估

Agent 对自己输出的评估不可信。“让 Agent 检查自己的工作”这一模式的可靠性远低于预期。

**替代方案**：独立评估 Agent + 计算型传感器 + 人类审查关键路径

### 反模式 3：无限重试循环

允许 Agent 在 CI 失败后无限次重试，会浪费大量计算资源，且通常不会收敛到正确结果。

**替代方案**：设置硬性重试上限（如 Stripe 的两轮规则），超出后转交人类

### 反模式 4：过早追求无人值守

Stripe 的无人值守并行化（每周 1300+ PR）建立在极其成熟的 Harness 基础上。多数团队在 Harness 不成熟时就追求无人值守，会产生大量低质量输出。

**替代方案**：从深度参与（Hashimoto 模式）开始，随 Harness 成熟度逐步放权

### 反模式 5：一步到位的大任务

Agent 倾向于一次做完所有事，结果上下文窗口耗尽，留下半成品。

**替代方案**：任务分解到可在单次会话内完成并验证的粒度；使用进度文件支持多会话连续性

### 反模式 6：用 Harness 补偿模糊需求

任何传感器都无法可靠捕获“问题误诊”、“误解指令”这类问题。如果人类没有清晰地指定期望，Harness 无法兜底。

**替代方案**：在执行阶段之前，人类审查规划阶段的输出，确认 Agent 理解了正确的目标
