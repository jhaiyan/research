### Harness Engineering 🔥

- **定义**：Harness Engineering 是一种 AI 工程学科，其核心公式为 **Agent = Model + Harness**。Model（模型）是原始推理引擎，Harness（缰绳/约束系统）是围绕模型的一切：系统提示、CLAUDE.md/AGENTS.md 文件、工具、MCP 服务器、Hooks、沙箱、子代理、反馈循环、记忆、权限、可观测性和恢复路径 [🔗](https://addyosmani.com/blog/agent-harness-engineering/ "Agent Harness Engineering") [🔗](https://martinfowler.com/articles/harness-engineering.html "Harness engineering for coding agent users")。其核心操作原则（Hashimoto Loop）为：“每当发现代理犯错时，花时间设计一个解决方案，使代理永远不会再犯同样的错误” [🔗](https://mitchellh.com/writing/my-ai-adoption-journey "My AI Adoption Journey")。
- **起源追溯**：Mitchell Hashimoto（HashiCorp 联合创始人）于 **2026 年 2 月 5 日** 在其个人博客《My AI Adoption Journey》中首次公开使用该术语 [🔗](https://mitchellh.com/writing/my-ai-adoption-journey "My AI Adoption Journey")。Viv Trivedy（LangChain 工程师）于 2026 年 3 月 10 日首次明确提出“Agent = Model + Harness”公式 [🔗](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness "The Anatomy of an Agent Harness")。Birgitta Böckeler（Thoughtworks）于 2026 年 4 月 2 日在 Martin Fowler 网站发表形式化分类法，引入“Guides（引导）与 Sensors（传感器）”的标准词汇 [🔗](https://martinfowler.com/articles/harness-engineering.html "Harness engineering for coding agent users")。行业共识为：“Mitchell named it; Viv defined it” [🔗](https://www.thedeepfeed.ai/posts/2026-05-09-agent-harness-engineering-the-discipline/ "Agent harness engineering: the new discipline, decoded")。
- **提出背景**：随着模型能力趋同（Claude、GPT-4、Gemini 性能差距缩小），模型本身不再是竞争优势。Harness Engineering 将工程重点从“调优模型”转向“设计模型运行的环境”。LangChain 仅通过更改 Harness（模型不变）将 Terminal Bench 2.0 得分从 52.8% 提升至 66.5% [🔗](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness "The Anatomy of an Agent Harness")。arXiv 上已出现至少 5 篇相关学术论文 [🔗](https://arxiv.org/html/2605.13357 "AI Harness Engineering: A Runtime Substrate") [🔗](https://arxiv.org/html/2604.25850v2 "Agentic Harness Engineering")。
- **使用场景**：编码 Agent 可靠性提升（Guides + Sensors）、生产级 Agent 部署（OpenAI 内部 Harness 团队 5 个月生成约 100 万行代码）、企业级受监管环境（Bayer PRINCE 平台）、自动化 Harness 演化（AHE 框架 10 次迭代将 pass@1 从 69.7% 提升至 77.0%）。
- **交叉验证**：Martin Fowler 网站、Google（Addy Osmani）、O'Reilly Radar、Simon Willison、Hugging Face、arXiv 多篇论文、Atlan、Port.io、amux.io 等多家独立平台均独立确认和讨论该概念。
- **争议与质疑**：（1）“旧酒装新瓶”——批评者认为只是将平台工程、SRE 等已有学科重新包装 [🔗](https://haverin.substack.com/p/what-is-harness-engineering-ai-hype "What is Harness Engineering?")；（2）Bitter Lesson 悖论——Harness 工程师频繁引用 Sutton 的 Bitter Lesson，却同时在模型周围手工设计复杂编排系统 [🔗](https://haverin.substack.com/p/what-is-harness-engineering-ai-hype)；（3）METR 研究发现 Harness 对 Agent 自主性影响有限——Claude Code 专用 Harness 相比简单 ReAct 循环仅在 50.7% 的样本中胜出 [🔗](https://haverin.substack.com/p/what-is-harness-engineering-ai-hype)；（4）Gödel/Vassilev 数学上限——NIST 科学家证明任何有限规则集（包括 Harness 架构）都不具有普遍鲁棒性 [🔗](https://dev.to/bala_paranj_059d338e44e7e/the-harness-is-half-the-architecture-heres-the-half-thats-missing-1fb9)；（5）Agentic vs. Agentive 学术批评——MBZUAI/CMU 论文批评 Harness 方法将代理结构外部化到人类设计的脚手架中，从根本上限制了可扩展性 [🔗](https://arxiv.org/pdf/2606.23991v1/)。

### Loop Engineering 🔥

- **定义**：Loop Engineering 是一种 AI 工程范式，指设计一个自动化系统来替代人工逐轮提示 AI Agent——由系统自主地触发 Agent、验证输出、决定重试或停止。一个完整的 Loop 规范包含五个部分：触发器（Trigger）、目标（Goal）、执行阶段（Execution）、验证步骤（Verification）和停止规则（Stopping Rule），外加持久化记忆（Memory）[🔗](https://addyosmani.com/blog/loop-engineering/ "Loop Engineering - Addy Osmani") [🔗](https://arxiv.org/html/2607.00038v1 "Stop Hand-Holding Your Coding Agent")。
- **起源追溯**：该概念于 2026 年 6 月初由三位独立人物几乎同时提出：Peter Steinberger（OpenClaw 创建者，现任职 OpenAI）于 2026 年 6 月 7 日在 X 发布获得超 800 万次浏览的帖子 [🔗](https://www.latent.space/p/ainews-loopcraft-the-art-of-stacking "AINews: Loopcraft")；Boris Cherny（Anthropic Claude Code 负责人）在数天前发表类似观点 [🔗](https://fourweekmba.com/claude-code-loops-boris-cherny-next-paradigm/ "Claude Code Creator Says Loops Are As Big a Step as Agents")；Addy Osmani（Google Chrome 工程负责人）于 2026 年 6 月 7 日正式命名该概念并给出系统化定义 [🔗](https://addyosmani.com/blog/loop-engineering/ "Loop Engineering")。Sandeco Macedo 于 2026 年 6 月 28 日在 arXiv 发表首篇正式学术论文 [🔗](https://arxiv.org/html/2607.00038v1 "Stop Hand-Holding Your Coding Agent")。
- **提出背景**：AI Coding Agent（Claude Code、OpenAI Codex）的成熟使人工逐轮提示成为瓶颈。发展脉络为：ReAct（2022）→ AutoGPT（2023）→ The Ralph Technique（2025 年 7 月）→ 原生工具支持（2026 年 5-6 月）→ 概念爆发（2026 年 6 月）。Loop Engineering 位于四层 AI 工程栈的顶端：Prompt → Context → Harness → Loop [🔗](https://www.codecentric.de/en/knowledge-hub/blog/loop-harness-context-engineering-explained "Loop, Harness, Context Engineering Explained")。
- **使用场景**：依赖版本升级、代码批量重构、不稳定测试修复、代码审查自动化、CI 失败自动修复、每日 Issue 分类、PR 自动管理。这些场景的共同特征是：任务重复频率高、成功标准可机器验证、预算可承受失败重试 [🔗](https://blackmatter.vc/lab/loop-engineering-an-honest-verdict-from-someone-who-actually-runs-agent-loops "Loop Engineering: An Honest Verdict")。
- **交叉验证**：O'Reilly Radar 转载、Latent Space AIEWF 2026 趋势报告、GitHub 开源实现（cobusgreyling/loop-engineering，约 8940 星）、独立指南站点（loopengineering.run）、Microsoft CEO Satya Nadella 使用“Loopcraft”术语、AIEWF 2026“The Great Loops Debate”专题辩论。
- **争议与质疑**：（1）概念并非全新——批评者指出本质上是“while 循环 + LLM 调用”，是 ReAct 模式的重新包装 [🔗](https://johnsonlee.io/2026/06/26/fooled-by-loop-engineering.en/ "Don't Let Loop Engineering Fool You")；（2）Token 成本高昂——Agent 循环消耗约 4 倍于普通聊天的 Token，Boris Cherny 本人被报道每月消耗高达 13 万美元的 Token [🔗](https://www.theregister.com/ai-and-ml/2026/06/24/loop-engineering-latest-ai-buzzword-still-needs-humans-in-the-loop/5261735 "Loop engineering, latest AI buzzword, still needs humans in the loop")；（3）理解债务（Comprehension Debt）——Loop 生成的代码未经人类审查，开发者对自身系统的理解落后于代码库实际状态 [🔗](https://www.v12labs.io/blog/2026-07-18-loop-engineering-explained "Loop Engineering Explained")；（4）概念迭代过快——仅六周后 Peter Steinberger 本人发问：“Are we still talking loops or did we shift to graphs yet？” [🔗](https://www.v12labs.io/blog/2026-07-18-loop-engineering-explained)。

### Graph Engineering 🌱

- **定义**：Graph Engineering 是将多智能体系统设计为显式图结构（Explicit Graph）而非隐式循环（Implicit Loop）的工程学科。其核心三要素为：（1）节点是能力单元——每个节点执行一项可测试、可替换的单一任务；（2）边是决策——带类型的转换在节点间传递状态；（3）状态是带 Schema 的检查点对象——在每次边跨越时进行状态检查点保存，支持审计追踪和故障恢复 [🔗](https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase "We Are Entering the Graph Engineering Phase")。核心论断：“循环没有死，它被降级了。Loop Engineering 是单个上下文窗口内发生的事，Graph Engineering 是上下文窗口之间发生的事” [🔗](https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase)。
- **起源追溯**：术语由 Josh C. Simmons（Dr. J）于 **2026 年 7 月 4 日** 在其博客《We Are Entering the Graph Engineering Phase》中首次提出 [🔗](https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase)。随后由 Peter Steinberger 于 2026 年 7 月 18 日在 X 以一条约 575K 浏览量的推文引爆传播 [🔗](https://explainx.ai/blog/graph-engineering-ai-agents-multi-agent-organizations-2026 "Graph Engineering: Wire Multi-Agent Orgs After Loops")。学术前身可追溯至 GPTSwarm（Zhuge 等人，ICML 2024），首次将语言智能体系统形式化为可优化的计算图 [🔗](https://www.alphaxiv.org/abs/2402.16823 "Language Agents as Optimizable Graphs")。
- **提出背景**：三个驱动力推动转变：（1）模型能力突破阈值，瓶颈从“能否完成一步”转向“能否协调一千步”；（2）企业生产环境要求审计追踪、可恢复性、审批关卡和预算上限；（3）并行化（Fan-out/Fan-in）是最廉价的性能杠杆，而循环没有表达并行的原语 [🔗](https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase)。
- **使用场景**：多专业分工协作、并行 Fan-out/Fan-in、企业级可审计工作流、确定性多步编排（GraphBit 在 GAIA 基准上达到 67.6% 准确率 [🔗](https://arxiv.org/html/2605.13848 "GraphBit")）、意图驱动的图编译（MASFactory 将实现从 1511 行代码减少到最少 45 行 [🔗](https://arxiv.org/html/2603.06007 "MASFactory")）。
- **交叉验证**：TrueFoundry 企业级指南、Turing Post 深度事实核查、AI Builder Club 完整指南、explainx.ai 双层图架构分析、学术领域多个图中心化框架（Graph-of-Agents、Sigma、MASFactory、GraphBit）、开源生态（Graphiti 28.8K 星、ActiveGraph、Yggdrasil 等）。
- **争议与质疑**：（1）本质上是旧概念的重新包装——@DavidKPiano（XState 作者）指出状态机和图编排已存在数十年 [🔗](https://www.aibuilderclub.com/blog/graph-engineering-vs-loop-engineering)；（2）炒作周期极度压缩——Loop Engineering 仅存在约六周便被宣告“死亡” [🔗](https://www.turingpost.com/p/is-graph-engineering-real-why-everyone-is-talking-about-it)；（3）病毒式传播的声明被证伪——声称 Graph Engineering 在 Microsoft、Stanford 和 Anthropic“取代了 RAG”的帖子经事实核查发现数据不可泛化 [🔗](https://www.turingpost.com/p/is-graph-engineering-real-why-everyone-is-talking-about-it)；（4）四个“图”含义被混淆——控制图、知识图、执行轨迹和改进图被混为一谈 [🔗](https://www.turingpost.com/p/is-graph-engineering-real-why-everyone-is-talking-about-it)。AI Builder Club 的总结最为精辟：“Graph Engineering 是真实的且被过度营销的，两者同时成立” [🔗](https://www.aibuilderclub.com/blog/graph-engineering-vs-loop-engineering)。

### Context Engineering 🔥

- **定义**：Context Engineering 是指设计、管理和优化 LLM 推理时上下文窗口内全部信息（系统提示、用户查询、对话历史、检索文档、工具定义与输出、持久化记忆、输出格式约束等）的系统性工程学科。其核心问题是：“在当前这一步，模型应该看到什么信息，以什么顺序，以什么格式？” [🔗](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents "Anthropic: Effective context engineering for AI agents") [🔗](https://cloud.google.com/discover/ai-context-engineering "Google Cloud: What Is AI context engineering?")。
- **起源追溯**：2025 年 6 月 17 日，Cognition AI 的 Walden Yan 首次将 Context Engineering 描述为 Prompt Engineering 的“下一个层次” [🔗](https://tarancodes.in/wiki/context-engineering)。2025 年 6 月 18 日，Shopify CEO Tobi Lutke 在 X 上明确表示更喜欢“Context Engineering”这个术语 [🔗](https://simonwillison.net/2025/Jun/27/context-engineering/)。2025 年 6 月 25 日，Andrej Karpathy 转发并放大，提出著名类比：“LLM 就像 CPU，上下文窗口就像 RAM” [🔗](https://simonwillison.net/2025/Jun/27/context-engineering/)。2025 年 9 月 29 日，Anthropic 发布官方工程博客给予正式背书 [🔗](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。
- **提出背景**：在早期 Chatbot 时代，Prompt 几乎是模型的全部输入界面。但随着 AI 系统演进为多步 Agent，手写 Prompt 仅占模型实际所见内容的约 5%。其余 95%——检索文档、工具输出、记忆、对话历史——需要一套独立的工程学科来管理 [🔗](https://memx.app/blog/prompt-engineering-is-dead-context-engineering-won/)。三个趋势汇聚：模型能力足够强使上下文质量成为瓶颈、上下文窗口增长到百万 Token 级别引发“Lost in the Middle”问题、Agent 使上下文动态化。
- **使用场景**：生产级 AI Agent 系统的上下文组装与隔离、RAG 系统的完整 Pipeline 编排、多 Agent 协作的 Sub-Agent 上下文隔离、企业级 AI 部署（Spotify 合并 1500+ AI 生成的 PR，Rakuten 在 1250 万行代码库上实现 99.9% 数值准确率）、结构化人机协作（五角色上下文包将平均迭代周期从 3.8 轮降至 2.0 轮）。
- **交叉验证**：arXiv 上至少 5 篇以“Context Engineering”为标题的论文（含分析 1400+ 篇论文的综述 [🔗](https://arxiv.org/abs/2507.13334)）、Anthropic/Google Cloud/IBM/Elastic 主流厂商正式定义、Stanford CS 224G（2026）纳入课程体系、DataHub 2026 年报告显示 95% 的 IT 领导者认为 Context Engineering 对扩展 AI Agent 至关重要、LangChain 发布 context_engineering GitHub 仓库。
- **争议与质疑**：（1）“换汤不换药”——多位评论者指出本质上是 Prompt Engineering 的重新包装 [🔗](https://pub.towardsai.net/karpathy-said-kill-prompt-engineering-heres-what-he-actually-meant-8c735fbabd20)；（2）“对失败的承认”——Chris von Csefalvay 指出 Context Engineering 的存在本身就是“对失败的承认”，Agent 本应自主发现和组装所需信息 [🔗](https://chrisvoncsefalvay.com/posts/context-engineering/)；（3）“打破可及性承诺”——Praveen Seshadri 批评其将普通人能理解的事情替换为普通人无法操作的事情 [🔗](https://ai.plainenglish.io/context-engineering-is-not-the-answer-7f9565b2ccc2)。各方均认可 Context Engineering 所描述的工作本身具有实际价值，争论在于这个标签代表的是真正的范式进步还是下一个炒作周期重命名。

### Agent Data Injection（ADI）🌱

- **定义**：Agent Data Injection（ADI）是一种新型间接提示注入攻击类别，攻击者通过将不可信数据伪装为可信数据（如安全关键元数据、资源标识符、工具调用记录等），使 AI Agent 在继续执行用户原始任务的同时，基于被篡改的“事实”做出错误决策。其核心技术为“概率分隔符注入”（Probabilistic Delimiter Injection）——利用 LLM 对结构分隔符的概率性解析特性，注入不精确的分隔符序列，使模型将攻击者控制的字段误读为合法的结构化边界 [🔗](https://arxiv.org/html/2607.05120 "Agent Data Injection Attacks are Realistic Threats to AI Agents") [🔗](https://cloudsecurityalliance.org/artifacts/agent-data-injection-a-new-attack-class-beyond-prompt-injection "CSA: Agent Data Injection")。
- **起源追溯**：由首尔大学、UIUC 及 Largosoft 的研究团队于 **2026 年 7 月 6 日** 在 arXiv 上首次提出（arXiv:2607.05120）[🔗](https://arxiv.org/abs/2607.05120)。Cloud Security Alliance（CSA）AI Safety Initiative 于 2026 年 7 月 16-17 日发布正式研究笔记，将其认定为“超越提示注入的新攻击类别” [🔗](https://labs.cloudsecurityalliance.org/research/csa-research-note-agent-data-injection-adi-20260717-csa-styl/)。研究团队已向 Anthropic、OpenAI 和 Google 进行了负责任披露，三家厂商均已确认相关问题。
- **提出背景**：ADI 的提出旨在解决现有 AI Agent 安全防御体系的结构性盲区。传统提示注入防御专注于将“指令”与“数据”分离，但 ADI 攻击并不注入指令，而是污染 Agent 隐式信任的元数据。研究显示，能将传统指令注入攻击成功率降至接近 0% 的防御措施，对 ADI 的攻击成功率仍高达 50%。CSA 指出，ADI 暴露的是“信任边界缺口”（Trust Boundary Gap），而非可修补的单一漏洞 [🔗](https://hackwednesday.com/blog/agent-data-injection-shifts-ai-security-beyond-prompt-hardening "HackWednesday: ADI Shifts AI Security Beyond Prompt Hardening")。
- **使用场景**：三种已验证攻击模式：（1）元素 ID 注入——在网页内容中植入伪造的 UI 元素标识符，诱使 Web Agent 执行任意点击操作；（2）来源注入——伪造 GitHub 评论的作者身份元数据，使编码 Agent 将攻击者误认为项目维护者；（3）工具调用注入——伪造先前的工具执行记录，诱使 Agent 合并恶意 PR。
- **交叉验证**：CSA AI Safety Initiative 发布独立防御评估分析、The Hacker News 独立报道、Codex Knowledge Base 独立技术分析、Anthropic/OpenAI/Google 厂商确认。研究团队已公开发布基准测试套件（GitHub: compsec-snu/adi）供独立复现，但截至 CSA 发布时，结果尚未被另一独立研究组复现。
- **争议与质疑**：（1）“并非新类别”之争——部分安全研究者认为 ADI 本质上是间接提示注入（IPI）的子类别，而非全新攻击类别 [🔗](https://www.mdpi.com/2078-2489/17/1/54)；（2）先例攻击的存在——EchoLeak（CVE-2025-32711）、CamoLeak（CVSS 9.6）、Invariant Labs（2025 年 5 月）等攻击在 ADI 论文发表前已利用数据结构而非指令注入 [🔗](https://realhacker.news/new-agent-data-injection-attack-can-make-ai-agents-misclick-or-run-attacker-commands/)；（3）数据/指令分离范式的根本性质疑——Abdelnabi 与 Bagdasarian（arXiv:2605.17634）通过 Contextual Integrity 理论论证任何固定策略都无法在不阻止合法流量的情况下阻止所有基于上下文的攻击 [🔗](https://arxiv.org/html/2605.17634)。HackWednesday 的折中立场将 ADI 描述为对现有提示注入讨论的“有益修正”而非全新类别 [🔗](https://hackwednesday.com/blog/agent-data-injection-shifts-ai-security-beyond-prompt-hardening)。
