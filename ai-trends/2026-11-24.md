## 摘要

本期的技术主线不是单纯扩大模型参数，而是重新分配计算、工具与验证责任。[Inkling 2 Mini](https://thinkingmachines.ai/news/inkling-2-mini/) 与 [GLM-5.4](https://www.i-scoop.eu/glm-5-4/) 同时采用 Loop Transformer，通过重复执行共享层增加每个 Token 的计算量；但这一思想可追溯到 2018 年的 [Universal Transformer](https://arxiv.org/abs/1807.03819)，不能视为本期新发明。两者证据强度也不相同：前者开放权重并披露较完整的自报评测，后者尚未公布旗舰模型完整基准、API 或权重。

Agent 工程正在从“提示与上下文”推进到“针对运行环境优化、由系统强制执行权限、用可检查流程交付代码”。[Hugging Face Harness Adapters](https://huggingface.co/blog/harness-adapters-at-scale) 在原始 Agent Harness 中进行强化学习；[Claude Ship](https://code.claude.com/docs/en/claude-ship) 将评审、修复与批准拆成三个受 GitHub 分支规则约束的 Agent；[OpenAI Performance Factory](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/) 用对抗复核与部署后验证闭合性能修复流程；[Codex Sandbox](https://openai.com/index/inside-the-codex-sandbox/) 与 [OpenShell](https://github.com/ai-openshell/openshell) 则把文件、网络、进程和凭据控制放在模型之外。

产业侧最重大的事件是 [Anthropic 完成 IPO 与同步私募](https://www.anthropic.com/news/ipo-close)：IPO 总募资额约 935 亿美元（未扣承销折扣与费用），同步私募约 260 亿美元，合计约 1195 亿美元。研究侧则应区分两类“验证”：[AlphaProof Code](https://deepmind.google/blog/introducing-alphaproof-code/) 为 Signal 核心密码学实现生成并由 Lean 检查证明，而 [黎曼猜想相关工作](https://techcrunch.com/2026/11/20/ai-claimed-a-solution-to-the-167-year-old-riemann-hypothesis-and-a-human-did-too/) 即使获得形式化检查与部分专家积极评价，也仍不能简写为“数学界已公认解决”。

### Loop Transformer（循环 Transformer）🔥

- **定义**：在推理时对同一组共享权重执行多次，使模型在不按相同比例增加存储参数的情况下增加每个 Token 的计算深度。[Universal Transformer](https://arxiv.org/abs/1807.03819) 已将其描述为带共享权重循环与动态停止机制的 Transformer 推广。
- **起源追溯**：可核验的直接思想源头之一是 Dehghani 等人 2018 年 7 月提交的 Universal Transformer；本期关注峰值由 11 月 20 日 [Inkling 2 Mini](https://thinkingmachines.ai/news/inkling-2-mini/) 与 11 月 23 日 [GLM-5.4](https://www.i-scoop.eu/glm-5-4/) 共同触发。因此，本期现象应称为“再受关注”，不能归功于单一厂商首创。
- **提出背景**：标准 Transformer 主要通过增加层数、宽度或参数扩展能力；循环结构把一部分扩展转为重复计算，适合探索参数效率、本地部署与按任务调整推理深度。
- **使用场景**：本地开放模型、编码与数学推理、长上下文任务，以及通过可变循环次数研究测试时计算。Inkling 的可变循环研究模型还用于观察循环次数与任务时域的关系。
- **交叉验证**：Inkling 2 Mini 存储 24 层，将中间 12 层执行三次，形成每 Token 48 次层调用；总参数 26.4B、激活参数 3.4B，官方称约 20GB 内存即可运行。GLM-5.4 则被报道为约 750B 参数，将 28 层共享块执行两次，形成 106 次层调用。两者证明该结构已被独立团队采用，但具体实现并不相同。
- **争议与质疑**：【有争议】“参数更少所以全面更高效”并不成立。循环会降低显存中的权重规模，却可能增加延迟；Inkling 数据主要为官方自报，GLM-5.4 尚无旗舰完整公开基准。其“比肩 2T 至 3T 参数模型”的说法应视为未独立验证的厂商主张。

### Agentic Robotics／Graph-as-Policy 🌱

- **定义**：Agentic Robotics 指多 Agent 系统主要在离线环境中编写、测试、诊断并迭代改进结构化机器人程序；[Graph-as-Policy（GaP）](https://arxiv.org/abs/2607.05369)是其实现之一，将感知、规划与控制组织为有向计算图。
- **起源追溯**：GaP 论文 v1 于 2026 年 7 月 6 日提交，v3 于 11 月 4 日更新，并列为 CoRL 2026 Spotlight。[项目总页](https://berkeleyautomation.github.io/agentic-robotics/)还记录了 Ken Goldberg 6 月 ICRA 演讲与 9 月文章；11 月 9 日 [Berkeley News](https://news.berkeley.edu/2026/11/09/recent-advances-in-ai-are-creating-a-paradigm-shift-for-robotics/)使该范式获得更广泛传播。
- **提出背景**：它试图在手工模型工程的可靠性与纯数据驱动策略的泛化之间建立第三条路径。Real2Sim 构建仿真，Agent 生成并修正计算图，Sim2Real 输出 ROS2 程序；最终执行阶段不需要 Agent 持续参与。
- **使用场景**：边界明确、物体与位姿存在变化的工业自动化，例如分拣、装填、爆米花制作和线缆插入；不应直接外推到开放家庭环境或高动态机器人任务。
- **交叉验证**：[GaP 项目页](https://graph-robots.github.io/gap)公开论文、代码、51 项初始技能与 8 个仿真／真实任务。项目报告约 5500 次试验；Make Popcorn 经 10 轮迭代由仿真 33% 提升至 94%，真实成功率为 90%。这些是项目方结果，尚不能视为独立复现。
- **争议与质疑**：当前周期时间仍高于约 7 秒／实例的工业目标；多数基准是准静态抓取放置，只有线缆插入使用力反馈。技能库扩大后的 Agent 编排、可变形物体、动态目标与移动物体仍未解决。“无需额外数据”也不等于无需几何模型、校准传感器、仿真和模块化技能。

### Agent Sandboxing（智能体沙箱）🌱

- **定义**：在模型之外，以操作系统、网络代理、进程继承和策略引擎强制限定 Agent 可访问的资源。模型可以提出权限升级请求，但是否授予由 Harness、用户或企业策略决定，[Codex 文档](https://openai.com/index/inside-the-codex-sandbox/)对此给出了明确边界。
- **起源追溯**：Sandbox 是传统操作系统与应用安全机制，并非 AI 原生概念。本期的增量在于针对自主 Agent 形成完整工程实现：OpenAI 于 11 月 18 日公开 Codex 沙箱细节，[OpenShell](https://github.com/ai-openshell/openshell)则以 CNCF 项目形式提供通用运行时。
- **提出背景**：编码 Agent 会执行任意命令、安装依赖、访问凭据并调用网络服务；仅靠系统提示无法构成安全边界。文件写入、出网域名、子进程与凭据注入必须由宿主环境执行。
- **使用场景**：本地与云端编码 Agent、MCP 服务、自动化研发、企业权限策略，以及需要在不完全信任模型输出的情况下运行工具的系统。
- **交叉验证**：Codex 在 macOS 使用 Seatbelt，在 Linux 使用 bubblewrap、seccomp-bpf 与 `no_new_privs`，在 Windows 使用 MXC，并通过沙箱外 HTTP／SOCKS5 代理执行域名规则。OpenShell 另提供内核级控制、策略变更形式化审查，以及只向获批端点注入真实凭据的机制。
- **争议与质疑**：沙箱不是绝对隔离。OpenAI 明确承认配置错误的网络服务或失效的自动停止可能破坏防护；Codex 默认广泛读取仍可能暴露 API Key，Deny Glob 展开与 MCP 服务默认未自动沙箱化也留下配置责任。形式化审查策略变更不等于证明整个运行时无漏洞。

### Harness Adapters（支架适配器）🌱

- **定义**：冻结开放模型基座，在未经改写的真实 Agent Harness 中采集交互轨迹，以 GRPO 训练 LoRA，使模型适应特定“模型—Harness—任务”组合，[Hugging Face 原始博客](https://huggingface.co/blog/harness-adapters-at-scale)将其命名为 Harness Adapters。
- **起源追溯**：本次可追溯的最早系统定义与完整公开实现是 Hugging Face 2026 年 11 月 20 日文章；其技术组成来自已有的 LoRA、GRPO、TRL 与 Agent RL，不能把每个组成部分都视为新发明。
- **提出背景**：通用后训练不一定优化某个 Harness 的工具格式、上下文压缩、反馈与失败恢复方式。直接在真实运行环境中训练，优化对象从单次答案变为完整工具轨迹。
- **使用场景**：开放权重编码模型、企业内部 Agent、固定工具链优化，以及建设可重复验证的私有任务集。由于需要基座权重，该方法不是对任意闭源 API 模型都适用。
- **交叉验证**：Hugging Face 针对 Qwen3.8-27B、Pi、OpenCode 与 Hermes Agent 发布 Rank-32 适配器。[i-Scoop 的独立技术分析](https://www.i-scoop.eu/harness-adapters/)进一步解释了训练与任务筛选；但性能数字仍全部来自原团队。
- **争议与质疑**：SWE-bench Pro 最难 51 题上，Pi 从 39.2% 升至 64.7%，但每题仅运行一次，样本很小；不同 Harness 的结果不能直接横比。Super-adapter 的合并权重在 Terminal-Bench 2.1 上选择，相关数字被作者自己标为“略乐观”；AutomationBench 上没有明确迁移收益。因此，“任务集比适配器更持久”比单一增幅更值得关注。

### Anti-AI-slop（反 AI 垃圾输出）🌱

- **定义**：Slop 指未经审慎生成与审核、被强加给接收者的低质量 AI 内容；工程语境中的 Anti-AI-slop 是用明确设计规范、确定性检查和人工审查减少模板化、粗糙或不可访问的交付物。[Simon Willison 的早期定义](https://simonwillison.net/2024/May/8/slop/)强调“不是所有 AI 内容都是 Slop”。
- **起源追溯**：Willison 于 2024 年 5 月 8 日系统阐述该词，并引用 @deepfates 前一天的帖子；这不是对全球首次用词的断言。本期工程关注主要来自 [Hallmark](https://github.com/Nutlope/hallmark) 与 [Impeccable](https://github.com/pbakaus/impeccable) 两个设计 Skill 项目。
- **提出背景**：编码 Agent 能快速生成页面，也容易重复渐变、卡片堆叠、空泛文案与不合理布局。Anti-AI-slop 将“不要生成看起来像 AI 的页面”改写为可执行规则与审查步骤。
- **使用场景**：前端生成与重设计、Agent 编辑后 Hook、CLI／CI 检查、可访问性与响应式审查，以及交付前的新上下文设计评审。
- **交叉验证**：Hallmark 使用 Floor、Reflex、Finish 三级门禁和真实浏览器多宽度检查；Impeccable 提供 62 条无需 LLM 的确定性规则，支持源码、渲染页面、GitHub Actions 与 SARIF 输出。两者采用了不同但可组合的实现路径。
- **争议与质疑**：Star 数只证明关注度，不证明设计质量提升。两个仓库均未给出独立用户研究或公认基准；确定性规则能够发现已知模式，却不能完整判断事实、任务适配与审美价值，过度套用规则也可能制造新的模板化。
