### Harness Engineering 🔥

- **定义**：通过设计围绕语言模型的"驾驭层"（Harness）——包括系统提示、工具、内存、编排、验证循环、沙箱和治理机制——来提升 AI Agent 可靠性的工程学科。核心公式为 **Agent = Model + Harness**。
- **起源追溯**：由 **Mitchell Hashimoto**（HashiCorp 联合创始人）于 **2026 年 2 月 5 日** 在其博客文章 [My AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey) 中首次提出。**Viv Trivedy**（LangChain）于 2026 年 3 月 10 日在 [The Anatomy of an Agent Harness](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness) 中首次提出 "Agent = Model + Harness" 公式，该文章获得约 73.3 万次浏览量。
- **提出背景**：随着 AI Agent 从实验走向生产，开发者发现模型能力本身不再是瓶颈——围绕模型的系统设计（上下文管理、工具接口、验证循环、错误恢复）才是决定 Agent 实际表现的关键因素。Harness Engineering 应运而生，将"提示模型"的实践系统化为"设计驾驭层"的工程学科。
- **使用场景**：编码 Agent 的可靠性提升、多工具编排、生产级 Agent 部署、Agent 行为治理与合规。
- **交叉验证**：多个独立来源汇聚到同一核心概念——[Martin Fowler / Thoughtworks](https://martinfowler.com/articles/harness-engineering.html) 发表了最全面的分类体系；[OpenAI](https://openai.com/index/harness-engineering/) 通过 Codex 案例研究提供了实证验证（100 万行代码，零行人工编写）；[Simon Willison](https://simonwillison.net/guides/agentic-engineering-patterns/how-coding-agents-work/) 在其 Agentic Engineering Patterns 指南中持续使用该术语；arXiv 上已有 7 篇以上同行评审论文直接研究 Harness Engineering。
- **争议与质疑**：Andrew D. Maynard（亚利桑那州立大学）认为"Harness"隐喻预设了命令与控制关系，可能使 AI 更加危险（"认知特洛伊木马"假说）。Stuart Miller 认为 Harness Engineering 只是**平台工程的重新包装**。Hacker News 上常见评论将其视为"好的文档和高测试覆盖率"的营销术语。此外，存在"大模型"与"大 Harness"之争——Boris Cherny（Anthropic）认为"所有秘方都在模型里"，而 Jerry Liu 认为"模型 Harness 就是一切"。

### Context Engineering 🔥

- **定义**：设计、管理和优化提供给生成式 AI 模型的信息的工程学科。它超越了提示工程，涵盖查询重写、混合检索、重排序、去重、上下文组装、语义缓存等 8 阶段流水线。**提示工程仅占第 7 步**，其余 7 步均为 Context Engineering 的范畴。
- **起源追溯**：术语最早由 **Riley Goodside**（Scale AI 首位 Staff Prompt Engineer）于 **2023 年 1 月 23 日** 在 [Simon Willison 博客](https://simonwillison.net/2023/Jan/23/riley-goodside/) 引用中提出，他将提示工程拆分为"Context Engineering"（选择与准备相关上下文）和"Prompt Programming"（编写清晰指令）。**Dex Horthy**（HumanLayer CEO）于 **2025 年 4 月 3 日** 在 [12-Factor Agents](https://www.hlyr.dev/blog/12-factor-agents) 中首次系统化提出。行业引爆点为 2025 年 6 月——Tobi Lütke（Shopify CEO）推文和 Andrej Karpathy 背书使其获得广泛关注。
- **提出背景**：随着 LLM 上下文窗口不断扩展（从 4K 到 1M+），"如何填充上下文窗口"取代"如何编写提示"成为核心挑战。Karpathy 提出了经典的 **CPU/RAM 类比**（LLM 是 CPU，上下文窗口是 RAM），称 Context Engineering 是"用正确信息填充上下文窗口的精妙艺术与科学"。
- **使用场景**：RAG 系统优化、多轮对话上下文管理、编码 Agent 的仓库上下文构建、生产级 LLM 应用架构。
- **交叉验证**：学术界（[Mei et al. 综述 1400+ 论文](https://arxiv.org/pdf/2507.13334v1)）、产业界（[Anthropic 官方工程实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[Gartner 创新洞察报告](https://www.deepset.ai/guides/gartner-innovation-insight-context-engineering)、[LangChain 官方文档](https://docs.langchain.com/oss/python/langchain/context-engineering)）均独立验证。Shopify 工程团队展示：仅改进提示时准确率从 71% 到 74%（+3%）；重构上下文而不改提示时从 71% 到 93%（+22%）。PostHog 已发布正式的 "Context Engineer" 职位招聘（薪资 $228K-$249.6K+）。
- **争议与质疑**：Hacker News 上存在大量辩论，许多评论者认为 Context Engineering 更像"技巧和启发式方法"而非真正的工程学科。批评者认为这只是对已有实践（信息检索、知识管理）的重新命名。支持者则认为术语的正式化有助于建立工程规范、工具链和最佳实践。

### Loop Engineering 🌱

- **定义**：设计迭代循环（plan-act-observe-evaluate）来驱动 AI Agent 自主运行的工程学科。核心理念是"**模型不是产品，围绕模型的循环才是产品**"——工程师不再手动提示 Agent，而是设计循环来自动提示 Agent。
- **起源追溯**：术语由 **Addy Osmani**（Google Cloud AI 工程总监）于 **2026 年 6 月 8 日** 在 Substack 文章 [Loop Engineering](https://addyo.substack.com/p/loop-engineering) 中首次提出。直接触发因素是 **Peter Steinberger**（PSPDFKit 创始人，2026 年 2 月加入 OpenAI）于 2026 年 6 月 7 日发布的病毒式 X 帖子（650 万+ 浏览量）："你每月一次的提醒：你不应该再提示编码 Agent 了。你应该设计循环来提示你的 Agent。"**Boris Cherny**（Anthropic Claude Code 负责人）独立描述了相同的实践，称自 2025 年 11 月以来未手动编辑过一行代码——他一直在编写循环。
- **提出背景**：随着编码 Agent 从辅助工具演变为自主开发者，手动逐条提示的方式变得不可持续。工程师发现，编写一个 while 循环让 Agent 自主迭代，比手动编写每一步提示更高效。Geoffrey Huntley 的"Ralph 循环"（`while :; do cat PROMPT.md | npx amp ; done`）是这一模式的早期实践先驱。
- **使用场景**：自主编码 Agent、持续改进循环、多步骤任务自动化、Agent 自我修正与迭代。
- **交叉验证**：Andrew Ng（DeepLearning.AI）于 2026 年 6 月 30 日发表 [Three Key Loops](https://www.deeplearning.ai/the-batch/three-key-loops-for-building-great-software) 框架。Simon Willison 于 2025 年 9 月发表 [Designing agentic loops](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/)，早于术语但描述了相同实践。arXiv 上已有 [首篇学术论文](https://arxiv.org/html/2607.00038v1)。GitHub 上出现多个相关仓库（[cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering) 8108 星）。
- **争议与质疑**：Token 成本是核心担忧——"$47,000 Agent 循环事故"（一个边界控制不当的循环整夜运行无上限）成为警示案例。Addy Osmani 本人警告"认知投降"风险：当循环自主运行时，工程师停止形成独立判断。Matt Pocock 警告"自我改进循环"中不良建议会随时间累积。此外，有评论者认为 Loop Engineering 只是现有 Agent 循环模式的重新命名，目的是增加 Token 消耗。

### Thin Harness, Fat Skills 🌱

- **定义**：一种 Agent 架构范式，主张保持调度层（Harness）轻薄，将领域知识和能力封装为可复用的"技能文件"（Skills）。核心公式为 **Fat Skills → Thin Harness → Fat Code**——技能文件厚重、调度器轻薄、生成的代码厚重。
- **起源追溯**：术语由 **Garry Tan**（Y Combinator CEO）于 **2026 年 4 月 9 日** 在 [X 推文](https://x.com/garrytan/status/2042925773300908103) 和 [GitHub 规范文档](https://github.com/garrytan/gbrain/blob/master/docs/ethos/THIN_HARNESS_FAT_SKILLS.md) 中首次提出。直接催化剂是 2026 年 3 月 31 日 Anthropic 意外将 Claude Code 完整源码（512,000 行 TypeScript）泄露到 npm——Tan 在阅读泄露代码后发现，"秘密武器"并非 AI 模型本身，而是围绕模型的驾驭层和技能系统。
- **提出背景**：Anthropic 于 2025 年 10 月 16 日发布 Agent Skills（SKILL.md 格式），首次引入可复用的、基于文件系统的技能文件概念。Simon Willison 称其"可能比 MCP 更重要"。2026 年初，多位独立研究者同时发现相同的架构模式——驾驭层应保持轻薄，领域知识应封装为可复用的技能文件。
- **使用场景**：Claude Code / Cursor / Codex 等编码 Agent 的技能管理、跨平台 Agent 技能复用、企业 Agent 知识库构建。
- **交叉验证**：Andrej Karpathy 的 CLAUDE.md 模板（111K+ 星标）、Viv Trivedy 的上下文片段（Context Fragments）、Daniel Miessler 的"苦涩教训工程"均独立得出相同结论。Addy Osmani 在 2026 年 4 月的综合文章中注意到："如果你观察当今顶级的编码代理，它们之间的相似度超过其底层模型。"Thariq Shihipar（Anthropic Claude Code 团队）于 2026 年 7 月 16 日提出补充框架"Thin Prompts, Thick Artifacts, Thin Skills"。
- **争议与质疑**：存在"薄驾驭层 vs. 厚驾驭层"之争——Harrison Chase（LangChain CEO）认为厚驾驭层扩展了模型能力，框架编码了最佳实践。共识是薄驾驭层适用于消费者/个人 Agent（可移植性、寿命长），厚驾驭层可能适用于企业流水线（可靠性、可审计性、合规性）。

### FACET Thesis 🧪

- **定义**：Feature-Aware Contracted Extension for Text（FACET）——一个为 AI Agent 提供工程执行层的框架，包含五个核心原则：**执行前先有合约**（Contracts Before Execution）、**上下文不等于记忆**（Context != Memory）、**运行时比智能体更重要**（Runtime > Agent）、**确定性是系统属性**（Determinism is a System Property）、**轨迹即问责**（Trace = Accountability）。
- **起源追溯**：由 **Emil Rokossovskiy**（rokoss21）于 **2022 年** 首次提出，最初作为确定性提示模板系统（v1.x）。2025 年经历重大重构（v2.0），转变为完整的编译器 + 合约系统。2025 年 9 月 7 日首次公开发布代码（[GitHub](https://github.com/rokoss21/facet-standard)）。2025 年 12 月 16 日在 [DEV Community](https://dev.to/rokoss21/facet-manifesto-1p7a) 发布 FACET 宣言，正式阐述该理念。
- **提出背景**：源于对非确定性 LLM 输出、缺乏合约以及临时提示工程混乱局面的挫败感。作者认为 AI Agent 需要类似操作系统的"内核空间"——一个在概率性模型和确定性执行之间提供合约保障的工程执行层。
- **使用场景**：需要确定性保证的生产级 Agent 部署、多步骤 Agent 工作流的合约验证、Agent 行为审计与追溯。
- **交叉验证**：FACET 的五个核心原则在 2026 年的多篇独立学术论文中得到形式化验证——[Agent Behavioral Contracts (arXiv:2602.22302)](https://arxiv.org/pdf/2602.22302)、[Sovereign Agentic Loops (arXiv:2604.22136)](https://arxiv.org/html/2604.22136)、[TRACE (arXiv:2607.12480)](https://arxiv.org/html/2607.12480v1)、[No Certificate, No Execution (arXiv:2605.24462)](https://arxiv.org/html/2605.24462v1)。"上下文 != 记忆"原则被 Mem0、Rohit Raj、Ninad Pathak 等多个独立来源独立得出。
- **争议与质疑**：FACET 项目是一个单人项目（约 200 个 GitHub 星标），但其主张的规模很大。没有发现独立的第三方采用证据或同行评审。2026 年 7 月 4 日，DEV Community 用户 zxpmail 发表实验文章，声称确定性 Agent 循环的四个实验全部失败，结论是"在当前技术栈下，这个问题没有工程解决方案"。
