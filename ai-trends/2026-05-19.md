### Claude Dreaming 🔥

- **定义**：Anthropic 推出的 AI Agent 自改进系统，让 Agent 在会话结束后进入"梦境"状态，通过后台分析历史会话记录、提取模式、整合记忆、生成可复用技能，使 Agent 在后续会话中表现更好。不涉及模型权重更新，仅通过外部记忆存储实现"学习"。
- **起源追溯**：**Anthropic 组织内部命名决策**，最早公开痕迹为 2026 年 3 月 31 日 Claude Code npm 包中 59.8 MB 源代码泄露暴露的 "Dream Mode" 内部架构，后于 2026 年 5 月 6 日 "Code with Claude" 开发者大会正式公开。命名灵感明确来自神经科学中的 REM 睡眠记忆巩固机制。
- **提出背景**：随着 Agent 执行复杂多步骤任务，跨会话记忆丢失成为主要瓶颈。Anthropic 观察到人类通过睡眠巩固记忆，于是设计了类似的机制：慢波睡眠阶段（整合原始记录）+ REM 阶段（跨 distant experience 提取模式）。
- **使用场景**：法律文档审查（Harvey 测试显示任务完成率提升 6 倍）、保险理赔处理（Wisedocs 文档审查时间减少 50%）、长期软件开发项目（Claude Managed Agents 自动积累团队编码规范）。
- **交叉验证**：概念本身有独立研究基础 —— UC Berkeley / Letta 的 "sleep-time compute" 论文（2025 年 4 月）早于 Anthropic 的命名；OpenClaw 社区已独立实现三阶段梦境系统（Light/REM/Deep）；Hermes Agent（NousResearch）有 "Dreaming" 功能请求；至少 15 家独立科技媒体进行了原创分析报道。
- **争议与质疑**：**【有争议】** (1) **安全风险**：prompt injection 可污染梦境记忆，Cisco 已披露 2026 年 3 月针对 Claude Code MEMORY.md 的攻击案例；(2) **拟人化命名批评**：Wired 发文《恳求 AI 公司停止用人类进程命名功能》，认为"梦境"创造不切实际的期望；(3) **技术新颖性质疑**：批评者认为只是 experience replay + 向量数据库 + 摘要的包装，没有真正的权重更新或 RL；(4) **性能声明可信度**：6 倍提升仅来自 Harvey 单一客户，缺乏独立基准测试。

### Harness Engineering 🔥

- **定义**：围绕 AI Agent 的完整工程化基础设施范式，核心公式为 **Agent = Model + Harness**。Harness 包含约束、工具、状态管理、可观测性、重试策略、评估器等一切让 Agent 从"能运行"到"可信赖"运行的基础设施。由 Mitchell Hashimoto（HashiCorp 创始人）于 2026 年 2 月 5 日首次命名。
- **起源追溯**：**Mitchell Hashimoto** 在个人博客 "My AI Adoption Journey"（~2026 年 2 月 5 日）中首次提出该术语，原文：*"I don't know if there is a broad industry-accepted term for this yet, but I've grown to calling this 'harness engineering.' It is the idea that anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again."* 随后 OpenAI 的 Ryan Lopopolo 于 2 月 11 日发布验证文章（1M+ 行 AI 生成代码、零人工编写、~1500 个 PR），Martin Fowler 网站的 Birgitta Böckeler 于 2 月 17 日和 4 月 2 日发表系统性分析，学术界于 5 月 13 日发布 arXiv 论文 "AI Harness Engineering: A Runtime Substrate"。值得注意的是，"Agent = Model + Harness" 公式由 LangChain 工程师 Vivek Trivedy 首创。
- **提出背景**：88% 的 AI Agent 项目在生产中失败。随着模型能力快速提升（Claude Sonnet 4.5 → Opus 4.5 → Opus 4.6），简单 wrapper 的价值迅速归零，但多天长周期工作流、组织集成、Agent 间协商等更难问题需要系统性基础设施。
- **使用场景**：Claude Code 的 ~50 万行 harness 源码、OpenAI Codex 的 agent-first 开发、LangGraph/CrewAI/Mastra 等框架的 orchestration 层、企业级 Agent 的 sandbox + review + eval 流水线。
- **交叉验证**：**极强** —— 25+ 独立出版物、8+ 学术论文、12+ 框架/工具、Frontend Masters 专业课程、Walking Labs 在线课程、GitHub  awesome-harness-engineering 资源列表（981 stars）、中文社区广泛讨论。SIG / KPMG / Gartner 的企业调研显示 94% 工程领导者认为当前度量标准不足。
- **争议与质疑**：**【有争议】** (1) ** rebranding 质疑**：多个来源承认 harness 中的每个组件在 2026 年 2 月前已存在（linter、test runner、CI pipeline、retry policy 等）， critics 认为"只是旧工具换了新名字"；(2) **临时性争论**：Anthropic 自身数据显示，为 Sonnet 4.5 编写的约束在 Opus 4.5 中变得不必要，Boris Cherny 观察到 "Claude Code 的 harness 任何给定代码行保质期约两个月"，估计 18 个月窗口将在 2027 年中期关闭；(3) **哲学局限**：PhilArchive 分析指出 harness 只能处理已知、可枚举的风险，对 tacit knowledge（默会知识）和未知未知无能为力；(4) **营销夸大**：OpenAI "100 万行零人工代码"声明被批评更像营销 pitch 而非同行评审的工程案例研究。

### Agentic Engineering 🔥

- **定义**：以 AI Agent 为默认代码生产方式的软件工程新范式。核心特征是开发者 99% 的时间不直接编写代码，而是编排 Agent、审核输出、设计约束。由 Andrej Karpathy 于 2026 年 2 月 4 日正式定义，恰好是他提出 "vibe coding" 一周年之际。
- **起源追溯**：**Simon Willison** 于 2025 年 10 月 14 日首次在公开文章中使用了 "agentic engineering" 一词（作为实践者标签，未声明原创）。**Andrej Karpathy** 于 2026 年 2 月 4 日在 X/Twitter 上正式定义并推广：*"'Agentic' because the new default is that you are not writing the code directly 99% of the time, you are orchestrating agents who do and acting as oversight. 'Engineering' to emphasize that there is an art & science and expertise to it."* 随后 Addy Osmani（Google Chrome Engineering Lead）同日发文帮助固化概念，IBM 于 2 月 27 日进行企业级正式化。
- **提出背景**：2025 年 11 月成为 coding agent 的"拐点"——GPT-5.1 / Claude Opus 4.5 使 agent coding "真正可用"。Karpathy 观察到从业者从 "vibe coding"（无代码审查的随性开发）转向需要更严格工程实践的专业模式，需要一个新术语来区分。
- **使用场景**：Claude Code / Codex / Cursor 等专业开发工作流、多 Agent 编排系统、AI 辅助软件架构设计、企业级 Agent 治理。
- **交叉验证**：**极强** —— 15+ 正式课程/学位项目（Johns Hopkins、Strayer University、IIIT Hyderabad）、953+ 招聘岗位（agentic-engineering-jobs.com 专门求职网站）、7+ 主流框架（LangGraph、CrewAI、AutoGen、Mastra 等）、ICSE 2026 AGENT 研讨会（25+ 论文）、IEEE Software 专刊、Business Insider / IBM / Gartner / McKinsey / Forrester 分析师认可。
- **争议与质疑**：**【有争议】** (1) ** rebranding 质疑**：Gartner 估计数千家声称 "agentic AI" 的供应商中仅 ~130 家是真正的 agent，大量是 chatbot / RPA 换皮；Karpathy 提出该词的部分动机被认为是替换带有负面 baggage 的 "vibe coding"；(2) **炒作周期**：Gartner 将 "agentic AI" 置于炒作曲线顶峰，预测 2027 年前 >40% 项目将因炒作、成本和风险被取消；(3) **信任危机**：Stack Overflow 2025 开发者调查显示信任 AI 输出的比例从 43% 下降至 33%，仅 3% "高度信任" AI 生成代码；(4) **就业冲击**：Dario Amodei 预测 5 年内 50% 入门级白领工作将被消除，ADP 数据显示 22-25 岁开发者就业下降约 20%。

### Context Engineering 🔥

- **定义**：为 LLM / AI Agent 设计、构建和管理完整信息环境的工程学科，核心问题从"我该如何措辞？"（prompt engineering）转变为"模型需要知道什么？"（context engineering）。由 Andrej Karpathy 给出经典定义："在上下文窗口中填充恰到好处的信息的精妙艺术和科学"。
- **起源追溯**：**Dexter Horthy**（HumanLayer）于 2025 年 6 月 3 日在 AI Engineer 会议上首次公开使用该术语，被认为是实际 coiner。**Tobi Lütke**（Shopify CEO）于 2025 年 6 月 19 日的推文成为 viral catalyst。**Andrej Karpathy** 于 2025 年 6 月 25 日的推文提供了经典定义（230 万+ 浏览量）。**Harrison Chase**（LangChain CEO）于 6 月 23 日进行行业正式化。**Gartner** 于 2025 年 7 月 28 日发布研究报告确认。**Anthropic Applied AI 团队** 于 2025 年 9 月 29 日发布技术文章进行技术正式化。
- **提出背景**：三大力量驱动：(1) 上下文窗口从 8K 扩展到 1M-10M tokens，使"窗口中放什么"比"如何措辞"更重要；(2) AI Agent 兴起，多轮、工具使用系统需要复杂的状态管理；(3) Prompt engineering 进入平台期——更好的提示词不再带来显著提升，更好的上下文成为差异化因素。
- **使用场景**：GitHub Copilot 上下文工程（VS Code 2026 年 5 月官方指南）、LinkedIn CAPT 平台（70% 更快的 issue 分流）、企业级 RAG 系统设计、多 Agent 协作中的信息共享与隔离。
- **交叉验证**：**极强** —— 20+ 独立来源（Anthropic、Microsoft、IBM、LinkedIn 官方博客）、LinkedIn Learning 官方课程、VS Code 官方文档、10+ 科技媒体、Reddit 开发者社区活跃讨论、2+ 招聘岗位（Contextual AI $160K-$200K、Braintrust 远程顾问）、LangChain / LlamaIndex / Mem0 / Zep / Letta / Atlan / LangSmith / Langfuse 等生产工具、3+ 学术研究框架（IBM DT-MDP-CE、PAACE、Directed Information gamma-covering）。
- **争议与质疑**：**【有争议】** (1) ** rebranding 质疑**：Serge Liatko（LAWXER CTO）称 context engineering "已经过时"且是"过渡性脚手架"，认为手动上下文管理无法扩展；Schaun Wheeler（Aampe Chief Scientist）认为应称为"context injection"而非"engineering"，真正的上下文需要按用户动态更新而非手动注入；(2) **Prompt Engineering 未死**：Chris Lema 等人反驳"prompt engineering 已死"的说法，认为需求不会消失，只是被纳入更广的体系；(3) **研究证据**：M-CALLM 论文发现某些场景下额外上下文"没有任何可测量收益"；(4) **共识**：管理 LLM 接收信息的学科确实关键且日益重要，但具体叫什么（context engineering、AI systems architecture 或其他）是次要的。
