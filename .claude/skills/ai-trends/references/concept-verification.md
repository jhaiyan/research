# 概念验证规则

本文件规定**单个代理**如何完成一个概念的全部验证。执行方式见 `SKILL.md` 第 4 节。

## 重要约定

- **每个概念由 1 个代理完成全部三项检查**，不再拆分为起源、独立验证、争议三个代理。
- 概念代理**不得再派生子代理**，也不得调用 Agent 工具。
- 单个概念的查询数不超过 `budgets.json` 中的 `concept_queries_per_concept`，页面抓取不超过 `concept_page_fetches_per_concept`。
- 概念总数不超过 `budgets.json` 中的 `max_concepts`；证据不足时可以少于上限，也可以为 0。

---

## 1. 起源追溯

目标：找到该概念**最早可核验**的公开出处。

优先级：

1. 提出者本人的博客、论文或官方文档；
2. arXiv 首次提交；
3. GitHub 仓库最早提交、Issue 或 PR；
4. 社交媒体首发讨论；
5. 社区最早讨论帖。

记录：最早日期、提出者或机构、原始链接、当时的原始表述。

起源研究不受本期时间范围限制，但仍受查询预算约束。找不到权威出处时标记 `【未经核实】`，并在结论中明确建议排除。

注意区分两类情况：

- 概念确为新提出；
- 概念是既有思想的新包装或再受关注。后者必须写明既有源头与本期关注点，不能写成首创。

## 2. 交叉验证

确认是否存在**独立于原始出处**的采用或讨论：

- 其他团队的实现、论文或工程实践；
- 社区中的自然讨论，而非原文引用。

若没有独立讨论，标记 `【未形成讨论】`，并建议降级或排除。

最低证据要求：原始出处加 1 个独立采用证据；不满足时不得在报告中作为“已成形概念”呈现。

## 3. 与旧范式对照

回答两个问题：

- 新方法解决什么问题；
- 旧做法是什么，现在换成什么。

有明确对照关系时用对照表，否则用两句话说明。

## 4. 成熟度判定

| 标记 | 判定标准 |
| ---- | -------- |
| 🔥 | 爆发期：本期 7 天内 ≥3 个独立来源，或出现多个独立实现 |
| 🌱 | 萌芽期：本期 30 天内 2 至 3 个来源，以解读文章为主 |
| 🧪 | 实验期：单一来源，或仅存在于仓库说明与未公开预印本 |

## 5. 输出条目

按下列结构输出，写入 `concepts.json` 并在报告中使用：

```markdown
### [术语] [成熟度]

- **定义**：[充分且必要的精确定义。]
- **起源追溯**：[提出者、机构、最早日期与原始链接。]
- **提出背景**：[概念要解决的问题与发展脉络。]
- **使用场景**：[主要应用场景。]
- **交叉验证**：[独立来源及其证据强度。]
- **争议与质疑**：[不同立场、权威质疑；确无争议时明确写明未发现显著争议。]
- **纳入建议**：[纳入／降级／排除，并给出理由。]
- **相关链接**：
  - [来源名称](URL)
```

## 6. 争议分析要求

必须明确回答：

- 该概念存在哪些争议；
- 不同立场分别是什么；
- 是否有权威来源的批评。

若确实不存在争议，明确写出“未从多个来源发现显著争议”，不得留空。

## 7. 结论与建议

验证完成后给出：

- 已核验的起源与证据链接；
- 独立佐证来源清单；
- 争议摘要；
- 成熟度判定及理由；
- 纳入报告、降级为背景说明或排除的建议与理由。
